Secure Video Access · Solution Walkthrough
Google Cloud · HIPAA-aligned · Proof of concept

Share surgical videos with hospitals securely, only after approval, and only for as long as needed.

A hospital asks for a recording. Your team approves it. The hospital user downloads it with strong sign-in, inside a time window you choose. Then access and files expire automatically. Patient data never leaves your Google Cloud environment, and every step is on the record.

The problem
📦

The files are very large

A single procedure can be hundreds of gigabytes to several terabytes. Email links and plain browser downloads fail, and a dropped connection means starting over.

🏥

The people are outside your company

Hospital staff don't have accounts with you. They still need strong sign-in, and must only ever see the videos approved for them.

🛡️

Every file is protected health information

Each share needs a named approver, encryption, a hard end date, guaranteed deletion, and an audit trail kept for six years.

The solution in one sentence

Your team logs each request and sends a secure invite. The hospital user sets a password and multi-factor sign-in. You approve with a download window, and only then are the requested videos placed in that user's private, read-only folder. Access and files expire on their own.

What you get
☁️

Data stays in your cloud

Videos go straight from your Google Cloud storage to the hospital. There's no third-party file service in between.

Technical architecture
How the solution is built on Google Cloud

Two separate front doors: a staff console behind Identity-Aware Proxy and a hospital-facing setup page and transfer server behind Cloud Armor and network allowlists. All compute runs in a private VPC, data is encrypted with per-hospital Cloud HSM keys, and every component logs to one audit vault. Everything is deployed with Terraform.

Request lifecycle (state machine)
REQUESTEDReviewer logs the emailed request. Domain checked. Nothing provisioned.
→
INVITEDSFTPGo account created with status=0, chroot to the per-request prefix. Email #1 with a 48-hour token.
→
PENDING APPROVALPassword (Argon2id) and TOTP saved; still disabled. TOTP secret removed from request state. Email #2.
→
APPROVEDFiles copied with the hospital CMEK and customTime = expiry; status=1 until expiry. Email #3.

Side exits: DECLINED (from REQUESTED) · REJECTED / REVOKED (from INVITED, PENDING or APPROVED: account disabled and staged files deleted). One active request per recipient.

Encryption & disposal
  • Cloud HSM keys (FIPS 140-2 Level 3), AES-256, 90-day rotation
  • One key per hospital for its videos, plus an infrastructure key for SQL, BigQuery and bucket defaults
  • Uniform bucket-level access and public access prevention on every bucket
  • Lifecycle rule: delete 1 day after customTime (= the approved expiry)
  • Safety net: delete anything older than max window + 2 days
  • Disable a key version to cut off one hospital; destroy it to crypto-shred
Audit & evidence
  • Data Access audit logs (read/write) on Cloud Storage and Cloud KMS
  • Structured JSON events from the console, setup page and SFTPGo (with client IP)
  • Cloud Armor request logs and Identity-Aware Proxy access logs
  • Log sink → Cloud Logging bucket, 2,190-day retention (lockable)
  • Log sink → BigQuery dataset (partitioned, CMEK) for reporting

Why SFTPGo
The secure transfer server hospital users connect to

SFTPGo is a mature, open-source file transfer server with a commercial Enterprise edition. In this solution, it's the only thing hospital users ever connect to for downloads. It reads the approved files straight from your Cloud Storage, and it enforces who can sign in, what they can see, and until when.

🔌 Speaks the hospital's language

SFTP for IT teams and scripts, a browser download page for everyone else, and WebDAV. These work with tools hospitals already use (Cyberduck, WinSCP, FileZilla), so there's nothing new to install.

⏯️ Handles huge files reliably

If a multi-terabyte download drops, it resumes from the exact byte where it stopped. Nobody has to start over.

☁️ Reads directly from Cloud Storage

No file servers or disks. SFTPGo streams from your bucket using short-lived Google credentials, so no keys are stored anywhere.

🔐 Strong sign-in for outside users

Password plus authenticator-app code on every sign-in, for people who don't have accounts with you.

📁 Each user sees only their folder

Every account is locked to one private folder, read-only, limited to the hospital's network, with an expiry date.

🤖 Driven by your approval workflow

The review console creates, enables, expires and revokes accounts automatically through SFTPGo's private admin API, so nobody configures it by hand.

Accounts database

Cloud SQL (PostgreSQL), private network only. It holds user records, password hashes and MFA settings, so any SFTPGo copy can serve any user. No videos are stored here.

Admin API: private only

Reachable only from the review console over your private network. It's never exposed to the internet.

Every action logged

Sign-ins, file reads, bytes and real client network address go to the six-year audit vault.

Why this is HIPAA-compliant

No software is "HIPAA certified". Compliance comes from three things:

  • A business associate agreement (BAA) covering every service that touches patient data. Here, that's only Google Cloud's BAA.
  • The right safeguards, configured and enforced, as shown in the table.
  • Operating it properly: approvals, reviews and incident response, with evidence.

SFTPGo is software you run inside Google Cloud services covered by the BAA. It isn't a separate vendor holding your data, so no extra BAA is needed. For production, the SFTPGo Enterprise edition adds a commercial license and vendor support.

Shared responsibility

Google secures the infrastructure under its BAA. This solution enforces the technical safeguards. Your organization remains responsible for the risk analysis, policies, workforce training and break-glass procedures, and the solution produces the evidence for those.
